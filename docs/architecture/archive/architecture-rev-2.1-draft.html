01

System architecture

1.1 Recommended architecture: modular monolith over one Postgres database

One deployable Node/Express process, internally split into feature modules, talking to one PostgreSQL database. The React frontend is a separate static build that only ever talks to this one backend. The only external service is Google (OAuth). The coupon workflow and the public walkthrough both fit inside this same shape without pushing toward microservices — the public page needs no backend at all (§1.3), and the coupon workflow is exactly the kind of transactional, correctness-critical work a monolith with real Postgres transactions is good at (§2.11, §4.5).

No scale pressure to justify microservices. 500 users and a handful of staff is a workload a single process handles without strain. Splitting it into services now would add network calls, partial-failure handling, and deployment complexity that buys nothing at this size.
Correctness needs real transactions. Booking → payment → ticket, and ticket redemption, are exactly the kind of "all-or-nothing" operations relational transactions exist for. Spreading them across services would force you to reinvent that guarantee with sagas or distributed locks — strictly worse for no benefit here.
Multi-college is a data dimension, not a deployment dimension. Every tenant-scoped table carries a collegeId (§2.9). Onboarding college #2 means inserting a row and some config — not standing up new infrastructure.
One codebase, one person learning full-stack. A monolith is easier to hold in your head end-to-end, which matters directly for the learning goals in CLAUDE.md §18.

Rule. A module calls another module's service function (e.g. paymentsService.simulatePayment(tx, …)), never its Prisma model directly, and never its controller/route file. Where several writes must succeed or fail together (booking + payment + ticket), the calling service passes down one Prisma transaction client so every write lands in the same transaction. reporting is the one exception: it only reads, so querying across modules' tables directly is safe and avoids forcing every module to expose a bespoke aggregation API.

Why a scan dispatcher NEW. A staff member standing at a counter shouldn't need two different camera screens depending on whether the person in front of them paid or is on a guest list. The QR payload itself carries a one-character type discriminator (T for ticket, C for coupon); scan is a thin router that reads that discriminator and calls into tickets or events, each of which still owns its own table, its own token-hash, and its own atomic redemption write (§4). The unification is in the staff-facing UI/endpoint only — the data stays exactly as separate as CLAUDE.md §8.6 requires.

Mutual exclusion, not just self-approval. CLAUDE.md §4.5/§8.4 says an event_organizer account can never simultaneously hold approving_authority — this is a role-grant-time rule, not only a per-request check. As defense in depth, the approval endpoint itself also independently checks request.createdByUserId !== decision.decidedByUserId at the moment of approval (§6.8) — so even a bug in the grant-time check can't produce a self-approved request.
REV 2.1 The grant-time check must be concurrency-safe, not just a pre-check. A plain "read UserRole, decide, then insert" in grantRole has the same TOCTOU shape as every other race in this document: two concurrent grant requests — one for ORGANIZER, one for APPROVING_AUTHORITY, both targeting the same user — can each read "the other role isn't held yet," both pass their check, and both insert. Neither the unique (userId, role) constraint nor an application-level pre-check prevents this: the constraint only blocks the same role being inserted twice, and it says nothing about two different role values for the same user. The fix is a real lock, not a cleverer check: 
BEGIN;
SELECT id FROM "User" WHERE id = $userId FOR UPDATE;   -- locks this user's row
-- within this same transaction, read UserRole for $userId
-- if the role being granted conflicts with one already held, ROLLBACK and return 409
INSERT INTO "UserRole" (user_id, role, granted_by_user_id, granted_at) VALUES (...);
COMMIT;
SELECT … FOR UPDATE takes an explicit row lock on the target User row for the duration of the transaction. A second concurrent grantRole call for the same user blocks at that SELECT until the first transaction commits or rolls back — so by the time the second transaction's mutual-exclusion check runs, it is reading the first transaction's committed result, never a stale snapshot. Whichever call's transaction acquires the lock first wins; the second one, now seeing the real committed state, is the one that gets rejected. Grants for two different users don't contend at all, since each locks only its own User row.

2.9 Database-wide decisions worth knowing cold

Money as integer paise, never float. ₹45 is stored as 4500. Floating point can't represent most decimal fractions exactly, so arithmetic on currency-as-float eventually produces off-by-a-paisa bugs; integers in the smallest unit sidestep the whole class of bug.
Price snapshot on Booking. priceInPaiseAtBooking is copied at booking time. If admin changes tomorrow's lunch price today, every already-confirmed booking keeps the price it was made at — a deliberate call confirmed in §11.
collegeId on every tenant-scoped table. Every service-layer query filters by the authenticated user's collegeId — never one supplied by the client. This is the entire multi-college strategy: no sharding, no per-college schema, just a column and a discipline about always filtering on it.
Timestamps in UTC, converted at the edge. Postgres timestamptz everywhere; Asia/Kolkata conversion happens explicitly in the cutoff-calculation code (§3), never relied on from server-local time.
Deactivate, don't delete. RosterEntry.isActive and User.isActive are booleans, not row deletions — history, audit logs, and foreign keys from past bookings stay intact.
Enums as native Postgres enums. Prisma maps TypeScript-style enums to real Postgres enum types — invalid values are rejected by the database itself, not only by application code.
REV 2.1 collegeId alone is a convention; composite foreign keys make it a constraint. Filtering every query by collegeId (above) stops a buggy query from reading across colleges. It does nothing to stop a buggy write from creating a row that points, say, a Booking in College A at a MealSchedule in College B — that's a plain single-column FK on mealScheduleId, and a single-column FK has no way to know about collegeId at all. The fix, where it's practical, is a composite foreign key that includes collegeId on both sides:

Child (collegeId, …)→ Parent (collegeId, id)
Booking(collegeId, mealScheduleId)MealSchedule(collegeId, id)
EventCouponRequest(collegeId, eventId)Event(collegeId, id)
GuestInvitation(collegeId, eventCouponRequestId)EventCouponRequest(collegeId, id)

A composite FK needs a matching unique constraint on the referenced pair, not just on the parent's primary key — so each parent table above also needs @@unique([collegeId, id]) (redundant with the PK on id alone, but it's what makes the pair referenceable). This is expressible directly in Prisma's schema language: a relation can declare multiple fields/references, e.g. on Booking: @@relation(fields: [collegeId, mealScheduleId], references: [collegeId, id]) against MealSchedule's @@unique([collegeId, id]). No raw migration SQL is required for this part. With it in place, an INSERT or UPDATE that tries to pair a child row's collegeId with a parent row from a different college is rejected by Postgres itself, as a foreign-key violation — not caught later by a query filter, a test, or a code review. This is deliberately not Row-Level Security: RLS would additionally rewrite every SELECT's visibility, which is more machinery than this pilot needs; composite FKs only close the specific "wrote a cross-college pointer" gap, at the cost of one extra unique index per parent table.

2.11 Coupon quantity accounting — exact source of truth for every count NEW, CRITICAL

Six of the eight numbers CLAUDE.md §8.5 asks the dashboard to track are never stored as a running total — they're computed live from ComplimentaryCoupon.status so they can never drift. Only two are stored counters, and both are written under one specific, concurrency-safe discipline (§4.5).

Why not just a database CHECK on the aggregate? A plain CHECK (generated_quantity <= approved_quantity) is necessary but not sufficient on its own: it stops an individual row from ever holding an invalid value, but it does nothing to coordinate two concurrent transactions that each read the current total, compute "mine fits," and then write — that's a classic read-then-write race, and the CHECK only catches it if the race happens to be won by the transaction that would have violated the limit anyway. The real fix is in §4.5: a single atomic conditional UPDATE that re-reads the committed total at the moment it takes the row's lock. The CHECK stays as a second line of defense against a future bug that writes to this table outside the proper service function — exactly the same "trust the database, not just the code" discipline as cutoff enforcement.

3.4 Transaction boundaries & failure recovery

Decision. Because V1 payment is simulated (no real gateway round-trip to wait on), create booking → simulate payment → issue ticket runs as one Prisma $transaction. If any step throws, Postgres rolls back all three writes — a student can never end up CONFIRMED with no ticket, or charged with no booking. If/when a real gateway is added, this three-step block is exactly what splits into "reserve, then confirm asynchronously on webhook" — flagged in §11 as a real future change, not a hidden gap today.

REV 2.1 Within this transaction, the payment step always writes a PaymentAttempt row first (§2.6) — SUCCEEDED in the normal simulated case, FAILED on the simulated-failure path that drives Booking to EXPIRED — before the Payment row itself is created/updated. This is what lets a failed attempt and a later successful retry both remain visible in the booking's history instead of one overwriting the other.

Duplicate submissions. A double-tapped "Book Now" sends two near-simultaneous POST /api/bookings for the same (userId, mealScheduleId). The second INSERT fails on the unique constraint (Postgres error code 23505); the service catches specifically that error and returns the first booking instead of a generic 500 — the request becomes idempotent by construction, not by a client-sent idempotency key. For operations without a natural unique constraint (e.g. admin overrides), an Idempotency-Key header is the general-purpose version of the same idea — worth knowing, not required in V1's limited surface for it.

QR & coupon security / concurrency

4.1 Token generation & storage

const rawToken = crypto.randomBytes(32).toString('base64url');   // goes into the QR
const tokenHash = crypto.createHash('sha256').update(rawToken).digest('hex'); // goes into the DB

The QR encodes { ticketId, rawToken } — never ticketId alone. ticketId identifies which ticket; rawToken proves the holder actually has the real ticket, the same way a password proves identity. The database stores only tokenHash, exactly as it would store a password hash: if the database were ever read by someone unauthorized, they'd get hashes that can't be turned back into a working ticket. A coupon's token is generated and stored the identical way (§2.10).

4.2 Redemption — verification steps

  1. Staff app scans QR → extracts {ticketId, rawToken}, sends POST /api/staff/tickets/redeem (or the unified /api/scan/redeem, §5).
  2. Load the ticket by ticketId, joined to its booking, student and meal schedule.
  3. Check ticket.collegeId === staff.collegeId — a staff member can never redeem another college's ticket, even one somehow guessed.
  4. Check sha256(rawToken) === ticket.tokenHash — proves possession of the real token.
  5. Check ticket.status === 'ISSUED' and booking.mealDate is today in Asia/Kolkata — a breakfast ticket from yesterday or a dinner ticket for tomorrow is rejected.
  6. Only if every check passes: the atomic redemption below.

4.3 The concurrency-safe redemption write

UPDATE "Ticket"
SET status = 'REDEEMED', redeemed_at = now(), redeemed_by_user_id = $staffId
WHERE id = $ticketId AND status = 'ISSUED';
-- Prisma: prisma.ticket.updateMany({ where: { id, status: 'ISSUED' }, data: {...} })
-- then check result.count === 1
Why this is safe under concurrency. This is a compare-and-swap: the WHERE status = 'ISSUED' clause is the "compare," the SET status = 'REDEEMED' is the "swap." If two staff devices scan the same physical ticket at nearly the same instant, Postgres serializes the two UPDATEs against that row using its own row-level locking — whichever runs first flips the status and returns count = 1; the second one's WHERE clause no longer matches anything, so it affects count = 0 rows. No application-level mutex or distributed lock is needed; the database's row lock during the UPDATE statement is the lock. The alternative — SELECT the ticket, check its status in JS, then UPDATE — has a race window between the read and the write (a classic TOCTOU bug: time-of-check to time-of-use) where two requests can both pass the check before either writes. The single conditional UPDATE closes that window entirely. The coupon redemption write (§4.5, §5) uses the identical pattern against ComplimentaryCoupon.

On count === 1: insert an Attendance row and set Booking.status = 'REDEEMED', in the same transaction. On count === 0: re-fetch the ticket's current state and respond 409 with "already redeemed at <time> by <staff>" — never a bare failure.

4.4 Manual (auditable) redemption

When a phone is dead or a QR won't scan, staff can look a student up by name/roll number and redeem manually. This still only requires a reason from a short dropdown (plus an optional note), and writes Attendance.method = 'MANUAL_OVERRIDE' alongside an AuditLog entry. kitchen_staff is allowed to do this directly — restricting it to admin-only would be impractical for someone actually standing at the counter — but every manual redemption is surfaced in admin's daily audit view, trading a small amount of trust for operational reality rather than hiding the trade-off.

4.5 Concurrency-safe coupon generation (the locked-counter pattern) NEW, CRITICAL

Redemption concurrency (§4.3) is "only one of these can win" — a boolean flip. Generation concurrency is a different shape: "the running total must never cross a line," across however many separate batch-generation calls happen, possibly from two different Kitchen Admins at once. The fix is the same family of technique — a single atomic statement whose WHERE clause re-checks the live value — but incrementing a counter instead of flipping a flag.

REV 2.1 Prisma naming convention, stated once here. Every model below uses camelCase fields in the Prisma schema, mapped to snake_case SQL columns with @map("snake_case_name") on each field and @@map("snake_case_table") on each model (e.g. generatedQuantity Int @map("generated_quantity") on a model mapped with @@map("event_coupon_request")). The raw SQL in this section uses exactly those mapped snake_case identifiers, so it is directly executable against the schema these tables describe — not illustrative pseudo-SQL.

REV 2.1 Rev. 2's Prisma snippet (updateMany({ where: { generatedQuantity: { lte: approvedQuantity - batchQty } } } )) was wrong: Prisma's ordinary filter objects can only compare a column against a literal or a bound parameter, never against another column on the same row. approvedQuantity - batchQty there is not a value Prisma can compute inside a where — there is no Prisma Client API for "this column's value, relative to that column's value." The comparison has to be expressed as real SQL, via $executeRaw, inside the same $transaction as the rest of the batch-generation work:

const result = await prisma.$transaction(async (tx) => {
  const [{ affected }] = await tx.$queryRaw<{ affected: number }[]>`
    WITH updated AS (
      UPDATE event_coupon_request
      SET generated_quantity = generated_quantity + ${batchQty}
      WHERE id = ${requestId}
        AND status = 'APPROVED'
        AND generated_quantity + ${batchQty} <= approved_quantity
      RETURNING 1
    )
    SELECT count(*)::int AS affected FROM updated;
  `;
  if (affected === 0) {
    throw new BatchExceedsApprovalError();   // triggers rollback; 409 to the client
  }
  const batch = await tx.couponBatch.create({ data: { eventCouponRequestId: requestId, quantity: batchQty, generatedByUserId: staffId } });
  await tx.complimentaryCoupon.createMany({ data: coupons /* batchQty rows, status GENERATED */ });
  return batch;
});

$queryRaw (or $executeRaw for a plain row-count) is Prisma's escape hatch for exactly this case: a conditional UPDATE whose WHERE clause compares two columns of the same row. The template-literal placeholders (${batchQty}, ${requestId}) are sent as bound parameters, not string-interpolated into the SQL text — Prisma's tagged-template raw-query API parameterizes them automatically, which is what keeps this safe from SQL injection despite looking like string interpolation. The affected-row count is read from the query result (here, via a RETURNING + count, since $executeRaw's own return value is the row count as a plain number and either form works); affected === 0 means the WHERE clause matched nothing — either the request wasn't APPROVED, or generating this batch would have exceeded approved_quantity — and the surrounding $transaction callback throws, which rolls back everything, including the CouponBatch/ComplimentaryCoupon writes that haven't happened yet.

Why two concurrent Kitchen Admins can't both succeed past the cap. Say approvedQuantity = 50 and generatedQuantity = 40, and two admins each try to generate a batch of 5 at the same instant. Postgres takes a row lock on the EventCouponRequest row for whichever UPDATE arrives first; that one's WHERE clause sees 40 + 5 = 45 <= 50, succeeds, and commits generatedQuantity = 45. Only then does Postgres let the second UPDATE acquire the lock — and it evaluates its WHERE clause against the now-current value of 45, not the stale 40 it might have read earlier: 45 + 5 = 50 <= 50 — still fine, both succeed, total is exactly 50. Try a third concurrent request for 5 more: it sees 50 + 5 = 55 > 50, its WHERE clause matches zero rows, affected === 0, and the service rejects it with a clear "would exceed approved quantity" error. No explicit SELECT FOR UPDATE or application-level lock is needed — the row lock Postgres already takes to perform the UPDATE is the lock, and it's held across the entire read-and-decide-and-write, closing exactly the gap a separate read-then-write would leave open.

On success, in the same transaction: insert the CouponBatch row, insert batchQty new ComplimentaryCoupon rows (status GENERATED), and auto-assign each to the next GuestInvitation for that request that doesn't already have a coupon (ordered by upload row order). If there are fewer unassigned invitations than the requested batch size, the batch is rejected before the counter is even touched — you can't generate more coupons than there are guests to receive them, a second natural cap beyond approvedQuantity.

4.6 Concurrency- and retry-safe coupon distribution REV 2.1, CHANGED

Rev. 2 treated distribution as "a plain transaction is fine, there's no scarce cap to race over." That's wrong in a different way than generation: there's no cap being raced over, but there is a state transition that must happen exactly once — and a network retry (the Kitchen Admin's app times out and resubmits, or two taps on "Distribute" register as two requests) is exactly the kind of duplicate call that, under a plain transaction, would increment distributedQuantity twice for one real distribution event. The fix is the same shape as redemption (§4.3): a conditional UPDATE that can only succeed once.

UPDATE coupon_batch
SET distributed_at = now(), distributed_by_user_id = $staffId
WHERE id = $batchId AND distributed_at IS NULL
RETURNING id;
-- affected === 0  → this batch was already distributed; return its existing
--                    distributedAt/distributedByUserId, not an error — the
--                    retry is a no-op, which is what "idempotent" means here
-- affected === 1  → proceed, in the SAME transaction:

Only the call whose conditional UPDATE actually matched a row (affected === 1) is allowed to also, in that same transaction: increment EventCouponRequest.distributedQuantity by the batch's quantity, flip every ComplimentaryCoupon in the batch from GENERATED to DISTRIBUTED, and write the AuditLog row for the distribution event. A second, concurrent, or retried call for the same batchId gets affected === 0 from the conditional UPDATE — proof that someone else's transaction already won — and simply returns the batch's current (already-distributed) state instead of repeating any of those four writes. This is the general pattern for "mark this done, exactly once, and tell a duplicate caller what already happened" — the same compare-and-swap idea as §4.3 and §4.5, applied to a one-time transition rather than a counter or a boolean flip.

4.7 Concurrency-safe approval modification NEW, REV 2.1

An Approving Authority can revise an already-approved request's quantity (ApprovalRecord.decision = 'MODIFIED', §2.10). The one invariant that must never break: the approved quantity can never be lowered below what's already been generated — doing so would retroactively make already-issued coupons illegitimate. This is enforced with the identical conditional-UPDATE technique as §4.5 and §4.6, run against the same row:

UPDATE event_coupon_request
SET approved_quantity = $newQuantity
WHERE id = $requestId
  AND status IN ('SUBMITTED', 'APPROVED')
  AND $newQuantity >= generated_quantity
RETURNING approved_quantity;
-- affected === 0 → reject: either the request is in the wrong state, or
--                  newQuantity would be lower than what's already generated.
--                  No ApprovalRecord is written and approvedQuantity is untouched.
-- affected === 1 → in the SAME transaction, insert the ApprovalRecord
--                  (decision: 'MODIFIED', decidedQuantity: newQuantity).
Why this coordinates correctly with concurrent generation, with no extra locking scheme. A modify-approval call and a batch-generation call (§4.5) both issue a conditional UPDATE against the same EventCouponRequest row. Postgres's ordinary row-level locking during an UPDATE already serializes any two statements that touch the same row — there is nothing extra to add. If generation commits first (raising generatedQuantity), a modify-approval attempt to lower approvedQuantity below that new, higher value then fails its own WHERE clause and is rejected. If the modify-approval commits first (lowering approvedQuantity), a subsequent generation attempt is evaluated against that new, lower cap, exactly as described in §4.5 — it simply has less room than it did a moment ago. Neither operation needs to know the other exists; each is just an atomic conditional UPDATE on a row Postgres is already serializing for them.

6.2 Returning login & role-aware entry

On callback, the backend first checks whether a User already exists for this email holding any staff/admin role via UserRole (KITCHEN_STAFF, KITCHEN_ADMIN, ORGANIZER, APPROVING_AUTHORITY, ADMIN, SUPER_ADMIN) — if so, log them straight in; the roster is a student eligibility list and never gates staff. Only if no such privileged account exists does the flow fall through to the student path (verified email → domain → active roster → find-or-create, grant STUDENT via UserRole).

6.3 Staff & admin provisioning — no public path, ever

Bootstrap admin. The very first ADMIN is created by a one-time seed script run manually against the production database by whoever controls deploys (e.g. npm run seed:admin -- --email=…). It is a script with direct DB access, not an HTTP endpoint — nothing remote can trigger it.
Promoting someone after that. An existing admin calls PATCH /api/admin/users/:id/roles, which writes a UserRole row (§2.3). If the target hasn't logged in yet, admin instead "invites" by email: a placeholder User row is created with the chosen role already granted; the first time that email actually signs in via Google, it attaches to the existing row instead of going through student provisioning.

6.4 RBAC enforcement

authGuard middleware resolves the session to req.user = {id, collegeId} from the server-side session store, then loads that user's UserRole rows — never from anything the client sends directly. roleGuard(['ADMIN']) then checks whether req.user's roles include the required one. Every protected route composes both.

Tenant isolation is a discipline, not a library. Every service-layer Prisma query on a tenant-scoped table must include collegeId: req.user.collegeId in its where clause. Treat a query missing that filter as a bug on sight in review. As a stronger second line of defense worth knowing about (optional, not required for the pilot): Postgres has native Row-Level Security, which can enforce this at the database layer itself so even a buggy query can't leak across colleges — a good V1.1 hardening step once the basics are working.

6.7 Session & cookie design EXPANDED, REV 2.1

Two cookies, never one: bc_session (college) and bc_guest_session (guest), each httpOnly, secure, signed, and read by exactly one middleware. authGuard resolves bc_session → {userId, collegeId}, then loads that user's UserRole rows on demand; guestAuthGuard resolves bc_guest_session → {guestInvitationId} and nothing else. The two middlewares produce differently-typed request objects (req.user vs. req.guest) so a route handler written for one shape cannot accidentally be satisfied by the other at compile time, not just at runtime. Neither middleware ever falls back to the other — a bc_guest_session cookie presented to authGuard (or vice versa) is simply not recognized, the same as no cookie at all; there is no shared parsing step where the two could be confused.

CHECK (type = 'COLLEGE' AND userId IS NOT NULL AND guestInvitationId IS NULL) OR (type = 'GUEST' AND guestInvitationId IS NOT NULL AND userId IS NULL) — the database itself refuses a session row that mixes the two identities. This is a real, server-side session store (a small Postgres table, not Redis — consistent with the "no infra beyond what's proposed" stance, §9.5), chosen specifically because it's the only design in this document's options that supports the explicit revocation this correction calls for: a signed, stateless JWT can't be revoked before its own expiry without a separate denylist, which is just this table under another name.

Cookie attributes. Both cookies: HttpOnly, Secure, SameSite=Lax (state-changing requests are POST/PATCH, which Lax already blocks cross-site; Strict would also block the OAuth-callback redirect's own cookie delivery, so Lax is the correct choice, not a weaker fallback). Path=/ for bc_session; Path=/ for bc_guest_session too — scoping by path is not the isolation mechanism here, the two separate cookie names and middlewares are (§6.5).
Lifetime. bc_session: a sliding expiry, e.g. 7 days of inactivity, refreshed on each authenticated request by bumping Session.lastSeenAt/expiresAt. bc_guest_session: a short, fixed expiry (e.g. 24 hours) re-issued on each sign-in — a guest's access to one event doesn't need a persistent session the way a returning student's does.
Session rotation on login. Every successful OAuth callback (college or guest) destroys any session id the request already carried and issues a brand-new Session row and cookie value — never reuses a pre-login session id. This is the standard defense against session fixation: nothing an attacker set in the browser before login survives login.
Logout. POST /api/auth/logout / POST /api/guest/auth/logout delete the Session row (not just clear the cookie) and clear the cookie. Because the session is server-side, a logout is immediately effective everywhere that session id was in use, not just in the browser that called logout.
Revocation on deactivation or role change. Deactivating a User (isActive = false), revoking a GuestInvitation, or changing a User's roles all, in the same transaction as that change, delete every Session row for that userId/guestInvitationId (or set revokedAt and have authGuard/guestAuthGuard reject any session with it set). The next request bearing that cookie finds no valid session and is treated as logged out — this is what makes "the roster check runs on every login" (§6.1) and "a revoked invitation blocks sign-in" (§6.6) actually bite for someone who is already logged in when the change happens, not only for their next fresh login.
CSRF protection. SameSite=Lax already blocks the cross-site POST/PATCH forgery pattern for both cookies. As defense in depth (and because some embedded/in-app browser contexts weaken SameSite enforcement), every state-changing request also requires a synchronizer CSRF token issued alongside the session and echoed back in a custom header (e.g. X-CSRF-Token) — a cross-site request can carry the cookie automatically but cannot read the token to echo it back.

9.2 Backups, migrations, rollback

Migrations: Prisma Migrate, committed and reviewed like code. prisma migrate deploy in production — never prisma db push, which skips writing a migration file and so leaves nothing to roll back to.
Backups REV 2.1, EXPANDED: daily encrypted backups (at rest, via the provider's default encryption or an encrypted bucket if self-hosting), retained on a 7-daily + 4-weekly schedule — seven most recent daily snapshots plus one snapshot per week for the four weeks before that, so a problem noticed a few weeks late is still recoverable. Backup access is restricted to whoever holds deploy/ops credentials, not the general admin role — a backup is a copy of every student's and guest's data, and broad access to it is itself a privacy exposure. Rely on the managed Postgres provider's automated daily backups where that tier includes this retention shape; if ever self-hosting Postgres instead, a daily pg_dump (encrypted at the destination) to restricted-access object storage, with lifecycle rules enforcing the same 7-daily/4-weekly retention, is the floor, not the ideal.
Restore testing NEW, REV 2.1: a periodic (e.g. monthly) restore drill — take the latest backup, restore it to a throwaway instance, and verify it actually boots and a few known rows read back correctly. A backup job reporting success is not proof the backup is restorable — corruption, a schema/version mismatch, or a silently-truncated upload are all failure modes that only a real restore attempt catches. The documented recovery procedure (below) is exercised by this same drill, not written once and left untested.
Documented recovery procedure NEW, REV 2.1: a short runbook — which backup to pick, how to restore it to a separate instance, what to verify before cutover (§9.2's existing "Recovery" card), and who is authorized to perform a production cutover — kept outside the database it describes (e.g. in the repo), so it's readable even when the database it's about is the thing that's down.
Rollback: prefer a new forward migration that corrects a mistake over editing a past one — the same reasoning as never rewriting pushed git history. A bad deploy rolls back by redeploying the previous build.
Recovery: restore a backup to a separate instance first and verify it, then cut over — never restore directly onto the live database.

11.2 Risks & bottlenecks

Single Postgres instance is a single point of failure. Acceptable at 500 users with a managed provider's backups; a real HA tier is a later, budget-gated upgrade, not a V1 flaw.
Cutoff correctness lives entirely in one piece of timezone-handling code. A bug there (server-local time instead of explicit Asia/Kolkata conversion) could silently let late bookings through or block valid ones — the single highest-value area for thorough boundary testing (§8).
The roster is a critical dependency, not just data. A stale or wrong upload can lock out real students or let former ones in. The dry-run preview and audit trail mitigate the technical risk; who actually maintains the roster, and how often, is a process risk this design can't fix by itself.
Redemption is the one place true concurrent writes happen in production, not just in tests — a counter rush with multiple staff scanning near-simultaneously. The atomic UPDATE pattern handles it correctly; at 500-user scale, Postgres serializing those writes is a non-issue, just worth understanding why.
A future real payment gateway breaks the "one atomic transaction" assumption. Flagged now so it's a planned change later, not a surprise (§3.4).
The guest-list Excel upload is as high-stakes as the roster upload it reuses the validator from — a bad upload means real people can't get in, or the wrong people can. Same dry-run/preview discipline should apply.
Google sub binding doesn't stop one person using two different Gmail accounts to double-claim under two invitations if both happen to be on the guest list — basic hygiene, not an anti-abuse system. Acceptable for a pilot; flagged so it isn't mistaken for bulletproof.
The "no background job" stance for expiry (§6.6, §9.5) means every expiry/expired-accounting check is request-time math. Correct and simple at 500-user/pilot-event scale; would need revisiting only if event volume grew enough that live computation became a real query-cost concern — not a V1 problem.

11.3 Questions that need a college-level decision, not an engineering one

  1. What exactly makes a roster entry "inactive" — an automatic date (e.g. semester end) or only explicit admin action? Decides whether roster expiry needs its own automation or stays a manual task.
  2. Is there a per-meal capacity cap in V1 (kitchen can only prepare N servings), or is booking uncapped for the pilot? Decides whether MealSchedule.capacity is enforced at booking time — another concurrency-shaped check, same family as redemption — or stays informational.
  3. If admin changes a price, does it apply only to new bookings, or retroactively to already-confirmed future ones? This design assumes new bookings only (§2.9) — confirm that's the intended rule.
  4. Who's authorized to perform a no-QR manual redemption — kitchen_staff directly, or must it route through admin? §4.4 proposes kitchen_staff-with-mandatory-reason as the operationally realistic choice.
  5. What happens to a whole meal's bookings if the kitchen can't serve it that day (ration shortfall, closure)? Needs an explicit "cancel every booking for meal X on date Y" bulk action — worth deciding whether that's in V1 scope or an accepted gap for the pilot.
  6. Does any college in the pilot or near-term future actually need more than one valid email domain? The schema already supports it (§2.2) — confirming it isn't over-engineering a want nobody has yet.

11.4 Ambiguities resolved while designing

"Bookings and booking items" (plural) for a V1 where a booking is really just one meal: resolved with a lightweight BookingItem/MenuItem layer that supports future add-ons or multi-dish bookings without a migration, while V1 behavior stays one item per booking and price stays per meal type, not per item.
"Configurable college email domains" alongside a single-college pilot: resolved by making domains a child table of college (many domains → one college), which satisfies the plural without building any actual multi-tenant complexity that isn't needed yet.

11.5 Unresolved decisions — flagged for explicit sign-off UPDATED, REV 2.1

  1. Coupon-to-guest assignment order. This revision auto-assigns coupons to guests in upload order as each batch generates. Is first-uploaded-first-assigned the right policy, or should the organizer be able to choose which guests get coupons first if a request is only partially approved?
  2. Does distribution trigger a guest notification (email) in V1? The schema records that a batch was distributed; it doesn't yet say anything about telling guests their coupon exists. Worth deciding before M13, since it changes what "claimed" even means operationally (a guest can't claim what they don't know exists). REV 2.1 Still open — not decided in this revision either.
  3. What happens to an already-CLAIMED coupon when its invitation is later revoked? Current design: revocation blocks future sign-ins but doesn't retroactively void a coupon the guest already has open. Is that the intended policy, or should revocation immediately void the coupon too? REV 2.1 Still open — this revision deliberately did not invent an answer, per the review's instruction.
  4. NEW, REV 2.1 Can a coupon be redeemed from DISTRIBUTED, or only from CLAIMED? See the callout in §2.10 — this changes one word in the redemption WHERE clause (§4.3) but is a real policy choice about whether a guest must have opened the app at least once before the coupon is usable at the door.
  5. NEW, REV 2.1 Is "expired" basis correct as Event.eventDate? See §2.11's Expired row — fine for a single-sitting event, but worth confirming before a multi-day event ever needs this accounting.
